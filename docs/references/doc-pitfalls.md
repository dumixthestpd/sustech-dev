# Pitfalls (encountered 2026-08-03)


- **Don't stack everything into one big doc.** If the pointer doc is the same size as the content, you've duplicated it. Halve the pointer.
- **Don't put "open issues" / "priority order" / "TODO" lists in the pointer.** Those are session-state and belong in issues/PRs or in memory, not in module docs. The pointer doc should be readable in 6 months without knowing what we're working on today.
- **Don't put "how to use this" or "why this shape" sections in module docs.** Procedure → skill. Meta → skill. Module docs describe what the code IS, not how to work with it.
- **Don't conflate top-of-file docstrings with workflow comments.** A docstring at the top of `tis.js` saying "if a UI element shows stale picked data, the fix is..." is workflow. It belongs in the skill (`sustech-dev` cascade contract section) or memory, not in the source file. Source-file docstrings state facts; skills/memory state procedure.
- **Don't repeat module-doc content in multiple files.** If `webui-architecture.md` has the state-var table, the source file's docstring points to it (with line numbers), not duplicates it. Self-contained for a reader means "I can find the fact by reading one file," not "I can find the fact even if the other file is deleted."
- **Before any `git checkout --` / `git restore` / `trash` / `rm -rf` / `mv`, show the user `git diff --stat` so they can confirm you're not discarding uncommitted work.** Triggered 2026-08-03: I ran `git checkout -- tis.js` thinking I was only discarding my own session's edits, lost ~637 lines of the user's prior uncommitted work. Same family as the 2026-07-26 `trash` incident. Iron rule: any operation that discards file contents requires `git diff --stat` first AND user confirmation when the working tree has uncommitted changes.
- **Before deleting or renaming any HTML element with an `id`, grep the JS for every `getElementById('<id>')` reference.** Triggered 2026-08-03: collapsed the old 4-tab structure into a 4-step stepper, removed `<input id="blocked-input">` and `<button id="bp-submit">` etc. Two JS bugs followed: (1) `solve()` threw `Cannot read properties of null (reading 'value')` on line 2490 because it still did `document.getElementById('blocked-input').value`; (2) `renderBlockGrid()` was guarded by `if (blockedEl)` so the step-2 block editor never rendered. The user reported "Mark unavailable is totally useless, solve doesn't respond" — both came from the same root cause: removing the HTML element without updating JS. Same family as the cascade contract — reference drift between template and JS. Fix pattern: when removing the source-of-truth DOM element, refactor to read from in-memory state instead (`BLOCKED` instead of `#blocked-input`), or guard the read with `if (el) el.value`. Don't just delete the element.
